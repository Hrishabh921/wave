# Changelog

This file tracks Wave's tier-by-tier build, not semantic-version releases - each entry is one roadmap tier, not a numbered version. Full detail for Tiers 10-22 lives in the matching "Shipped in Tier N" section of [`Readme.MD`](Readme.MD) and the matching "Status — shipped" block in [`docs/ROADMAP_BEAT_SARA.md`](docs/ROADMAP_BEAT_SARA.md); this file is a summary, not the source of truth.

## Tier 30 — Your own wake words: "baby", "babu", "dodo", "suar" (2026-11-18)

The user wanted "baby" as the main wake word, plus "babu", "dodo" and "suar" (the existing "hey wave", "hello wave" and "wake up" stay). Their log showed them saying "baby" again and again with nothing happening, and testing Wave's own Whisper model (base, language auto-detected) on synthetic samples showed why: a lone short word was often taken for another language - "dodo" came back as "ドードー" / "どうぞ", "suar" as "スワー" / "做了" / "So", Hindi context as Urdu script ("بابو", "دو دو") - and a lone "Baby" could score under the 0.35 confidence floor and be dropped. Fixes: while the mic waits for its wake word, the wake words lead Whisper's decoding prompt (`stt_engine.wake_hint`, set by the web mic worker) - 23 of 24 samples then came out right, and six non-wake samples (TV, chat, a song, noise) produced no false wake word; `voice/commands.py` also accepts a few known alternative spellings (`WAKE_SPELLINGS`: "Do-do", "Sua", Devanagari, Urdu, kana) but deliberately not everyday English words Whisper sometimes wrote instead ("So", "Sour"); and a transcript Whisper scored too low (now kept as `Transcript.rejected_text`) still wakes Wave when it is only a wake word. Settings -> Voice -> Wake Word -> "Custom..." now takes several comma-separated words (the first is the main one) and shows the active list; the bridge starts with the saved wake words. The user's settings now hold baby (main), babu, dodo, suar, hey wave, hello wave, wake up. 12 new tests (`tests/test_tier30_wake_words.py`).

## Tier 29 — Replies that arrive, and lips that move only with the voice (2026-11-18)

The user reported that replies were unreliable - sometimes "(no reply)", sometimes an error, usually very late after a long "thinking" - and that the Dodo character's lips kept moving while no voice came out. Their own log showed why. Every request in a session got "429 Too Many Requests": Groq's free tier allows 8,000 tokens a minute per model, a request was ~3,600 tokens, a reply that uses a tool needs two, and the mic - permanently AWAKE once woken - kept turning room noise into questions ("Gather real", "Gatya", "You have eaten."), each one another cloud request that also cut off the reply in progress. The Groq SDK then sat out each 429's Retry-After (~30 s, twice), the turn fell to a local Ollama that wasn't running (~9 s of Windows connection retries), and ended in a raw "System Error: ...". Fixes: the SDK client no longer retries by itself (`max_retries=0`); `WaveBrain._llm_create()` moves a rate-limited request at once to a backup model with its own quota (`LLM_FALLBACK_MODEL`, default openai/gpt-oss-20b on Groq), keeps a per-model cooldown from Retry-After, waits once if a model frees up within `LLM_RATE_LIMIT_WAIT_S` (10 s), retries a 5xx/dropped connection once, and otherwise answers "the AI service is busy - ask again in about N seconds" instead of an error; the Ollama fallback is skipped after a 0.4 s check when nothing listens (remembered 60 s); history sent with a request is capped (`LLM_HISTORY_CHARS`, 4,000 chars, no message over 1,200); tool lists dropped to `LLM_MAX_TOOLS`=20 and are no longer padded with tools the turn gave no sign of needing (small talk now carries 12, ~1,100 tokens instead of ~2,200). Web UI mic: while AWAKE, a transcript of three words or fewer, below `AWAKE_MIN_CONFIDENCE` (0.5), without the wake word and unknown to the intent router is ignored as noise, and AWAKE quietly returns to waiting for the wake word after `AWAKE_IDLE_SLEEP_S` (60 s) of nothing for Wave; recognized speech is now logged with its confidence. Chat: every reply carries a turn number back on chat_chunk/chat_done, so a cancelled turn finishing late can no longer end the next reply's bubble with "(no reply)" (which is also why answers were heard but not shown). Dodo: the avatar used to switch to SPEAKING the moment a reply was requested, and the page invented "chatter" when no audio curve had arrived - so her lips moved through every silent wait. Now the bridge marks SPEAKING only when TTS audio actually starts (voice/tts.py's on_playback_start, which also gives the web UI its time-to-first-audio figure), the mouth moves only from the loudness curve of audio really playing, and a stopped sentence stops the lips too. Measured against the real Groq account at a normal pace: five questions answered in 1.7-16 s, none failing (they took 60-80 s or failed before). 16 new tests (`tests/test_tier29_reply_reliability.py`).

## Tier 28 — Only the tools a request needs (2026-11-17)

Found while testing Tier 27 in the real app: every reply that needed the LLM was failing. Wave registers 180 tools and sent all of them with every request; Groq (like OpenAI) refuses more than 128 ("'tools': maximum number of items is 128"), so each request failed, fell back to Ollama (not running) and ended in an error or a tool-less answer. Cutting to 128 then hit Groq's free-tier limit of 8,000 tokens a minute: each tool definition costs ~55 tokens, so 128 of them plus the ~1,100-token system prompt was an 8,527-token request ("413 Request too large"). New `brain/tool_select.py` sends at most `LLM_MAX_TOOLS` (default 32, about 3,000 tokens) per request, picked for the turn: tools the conversation already called, the user's own drop-in skills, the strongest matches for the last two user messages (name and description words, with Hinglish synonyms such as awaaz -> volume, kholo -> open, mausam -> weather), twelve essentials (live information, web search, weather, time, date, calculator, reminders, open app/website, YouTube, notes, memory), then more matches, the everyday set and registration order. `WaveBrain._chat_completion`, its streaming twin and the Ollama fallback all use it. Most plain commands never reach the LLM anyway - brain/intent_router.py answers them directly. Checked against the real Groq account: a no-tool question answered in 1.5 s; no 400/413 errors. Still limited by the free tier itself: a reply that uses tools takes two or more requests, Groq also reserves the reply's max_tokens against the per-minute budget, so back-to-back tool replies get 429 and the Groq client waits and retries (a weather question took ~80 s while wttr.in was itself returning 503). 14 new tests (`tests/test_tier28_tool_select.py`), including 22 English and Hinglish requests that must each get their tool.

## Tier 27 — Lifelike avatar animation for the Dodo page (2026-11-17)

The user found the Tier 25 avatar's frame swaps unnatural (a blink squashed the eye area into a strip, talking stretched the mouth, the whole photo slid sideways) and asked for smooth, human-like expressions. LivePortrait (github.com/KwaiVGI/LivePortrait; MIT code, its bundled InsightFace detection models are for non-commercial use) re-draws the photo with real eyelids, eye movement, breathing, head motion, a smile and a mouth whose jaw drops instead of baring the teeth. On the user's RTX 3050 laptop GPU it manages about 7 frames a second, nowhere near live, so the clips are rendered once and played back. New `avatar/live_plan.py` describes four seamlessly looping clips as pure math (idle 9.6 s, listen and think 4.8 s, talk 3.2 s at six mouth openings). `avatar/live_render.py` renders them in a separate CUDA environment (`AVATAR_LIVE_PYTHON` / `AVATAR_LIVE_LP_DIR` in .env): 960 frames in about 5 minutes, about 32 MB, swapped in only when every clip is done. `avatar/live.py` runs that as a subprocess with progress, serves the files to the page from 127.0.0.1 behind a random token (only the files the manifest names), and turns each TTS utterance's audio into a 25 fps mouth-opening curve; `voice/tts.py` gained an `on_playback_pcm` listener, called just before each decoded utterance plays. The Dodo page draws the clips on a canvas at 25 fps, cross-fades between states starting the new clip at the frame whose head pose matches, and blends the two nearest mouth openings from the curve, so the lips follow Wave's real voice - for replies and for anything else spoken aloud. Settings → Avatar has a "Render lifelike animation" button with progress; building a new avatar renders again automatically, and a render made from an older photo is ignored. Without LivePortrait the page keeps the 5-frame rig. `avatar_rig/` is now in .gitignore (the photo, voice sample and renders are personal). 27 new tests (`tests/test_tier27_avatar_live.py`). Checked end to end in the real app on the user's laptop: the Dodo page runs the lifelike player, and a real TTS line's loudness curve (149 frames for a 6-second sentence) reaches the page and moves the mouth.

## Tier 26 — Web UI rebuilt to match the PyQt6 desktop UI (2026-11-14)

The user asked for `wave_web_start.pyw`'s web UI to look exactly like `wave_start.pyw`'s PyQt6 UI. Every desktop page was rendered offscreen as a reference (mic, workers and hotkeys stubbed out) and the web page rebuilt to match it with headless-Edge side-by-side comparisons: the same 210px sidebar, the 17 pages in the same order, the sliding page stack, Home's live page-preview tiles, the chat panel (bubbles with tails, reactions, live captions, activity banner, visualizer, attachments), circular gauges and sparklines, the spinning album disc, Files tree, Activity/undo rows, the Tier 21 management pages, Settings with all 10 tabs, the command palette (Ctrl+K) and the first-run onboarding wizard. `js/theme.js` carries `ui/theme.py`'s 11 themes (plus custom themes from `<DATA_DIR>/themes`, and the shared `last_theme` key), and the CSS is `build_stylesheet()`'s QSS translated rule by rule - including what Qt actually draws (it reads `"#00D4AA40"` as #AARRGGBB, which is where the olive active-nav highlight comes from; on scroll-wrapped pages the panels and controls are outlines only; it renders `font-weight: 600` as regular). Icons use the same Font Awesome 6 font file qtawesome draws the desktop icons with. New `webui/bridge_parity.py` (`ParityMixin`) gives the page every backend call the desktop widgets make, always through the same functions (db, AppController, FileManager, CalendarManager, skill loader, remote dashboard, ...), and starts the same background services as `MainWindow` (proactive engine, memory consolidation, thread supervisor, Ollama lifecycle, health check, weather, clipboard monitor, skill hot-reload, global hotkeys). The mic now runs for the whole session like the desktop's and the mic button switches AWAKE/SLEEPING. `clear_chat` no longer calls `db.clear_all()` (the desktop's "Clear chat" never wiped memory/reminders/to-dos). Chat replies are rendered as markdown by the bridge with raw HTML escaped, then sanitised again in the page. Deliberate differences from the desktop, each a desktop glitch rather than its design: "&" shows as "&" (Qt shows "Apps _Power"), chat markdown actually renders (the desktop's markdown path never runs because `_markdown_lib` isn't exported by `from ui.common import *`), toasts get the panel background (the desktop's parentless toast window gets no stylesheet), the Tier 21 Home tiles use their emoji instead of "⬜", and Top Processes lists real processes instead of an empty file-system header. The PyQt6 UI is unchanged. 34 new tests (`tests/test_tier26_web_ui_parity.py`). Run once in the real pywebview window on the user's screen (2026-11-17): every page and Settings tab rendered with no page errors, and the always-on mic picked up speech. That run led to two small fixes: a blank favicon, so the page stops requesting a missing `favicon.ico`, and the window now detaches from the bridge as soon as it starts closing, so a winding-down mic worker no longer makes pywebview log an ERROR. It also showed `edge-tts==7.2.8` being refused by Microsoft's voice service (HTTP 403), so both UIs had been speaking with the offline fallback voice; the pin is now `7.3.1` in `requirements.txt` and `requirements.lock`. Still untested in the real window: file dialogs and global hotkeys. Also at the user's request (2026-11-17), Wave's character - the Tier 25b avatar - moved off the top of the chat panel, where it left only a sliver of the chat visible while the mic was on, to a web-only sidebar page of its own, "Dodo", just above Chat; page indices now all go through `IDX` (the command palette had hard-coded numbers), with a test that `IDX`, the nav list and the build order agree.

## Tier 24 — A second UI technology, built with SARA's own stack (2026-11-08)

Not from a gap-analysis document - the user asked directly for Wave's UI to be rebuilt using SARA's own web technology (pywebview + plain HTML/CSS/JS) so future UI changes would be easy to make. New `webui/` package, launched by a new sibling script `wave_web_start.pyw`: a complete second UI covering chat, voice, and every management page, built with no framework and no build step. The original PyQt6 UI (`ui/`, `wave_start.pyw`) is completely unchanged - this is a sibling, not a replacement, and both UIs read/write the exact same settings file and database. `webui/bridge.py`'s `WaveWebBridge` is the single backend seam (pywebview's `js_api`), wired directly into the same backend singletons the PyQt6 UI already uses - no second implementation of brain/automation/database logic. Streaming events (chat chunks, mic level, captions) are ported from `ui/workers.py`'s `QThread` workers to plain `threading.Thread` subclasses with callbacks in place of Qt signals, deliberately kept a close structural mirror of the originals. A message from the web chat clears the exact same confirm-gate round-trip a desktop message does - no separate, weaker "web" path. Design-token CSS (`tokens.css`/`motion.css`) mirrors SARA's own frontend approach, making colors/spacing/motion a one-file edit. Tier 23's remote-dashboard server is reused completely unchanged from the new Settings page. 35 new tests (`tests/test_tier24_web_ui.py`); also found and fixed a real pre-existing test-suite bug while verifying this tier: two existing test files swapped `sys.modules["pygame"]`/`["edge_tts"]` for stand-ins and popped them back out, which could race with an unrelated test file's own module-eviction dance and intermittently produce a circular-import `AttributeError` in completely unrelated UI tests - fixed by patching the real, already-imported modules' attributes in place via `mock.patch.object` instead of ever touching their `sys.modules` entries. 2442 tests via `python -m unittest discover`, up from 2407. Bench unchanged (router 651/100%, redteam recall 96.09%/FPR 2.99%). Needs a real display and real audio hardware for: how the new pywebview window actually looks, and the full voice loop through its new worker path.

## Tier 23 — Remote mobile dashboard (2026-11-08)

Not one of the original roadmap's Tiers 1-22 - this one is post-roadmap, from a from-scratch comparison against a second reference project ("Jarvis"/Mark LVI, `claude/JARVIS_GAP_ANALYSIS.md`) that found Wave had nothing reachable off the desktop at all, while Jarvis ships a phone-paired web dashboard. New `remote/` package: a FastAPI+uvicorn web server, off by default, enabled from a new Settings → Remote page, paired to a phone by QR code (plus an 8-character typed fallback) instead of a password. Every message from the phone runs through the exact same `brain.think_stream()` a typed desktop message does - no separate, weaker code path - so a T2/T3 tool still has to clear the normal spoken/typed confirmation round-trip. Session cookies are HMAC-signed with a sliding TTL (no JWT library needed); "Regenerate pairing code" rotates the signing secret and signs every paired phone out at once. CSRF defense is a same-origin custom header plus `SameSite=Strict`, deliberately simple for a single-user LAN tool rather than a dedicated token library. Reachable only on the same Wi-Fi/LAN - nothing here opens a port on anyone's router. 63 new tests, 2404 up from 2341 (2407 via `unittest discover`); also fixed a latent `tests/_phase4_support.install_fake_module()` fragility this tier's own test file happened to expose under `xvfb-run` (same `BaseException`-vs-`Exception` class of bug Tier 22's bench fix already caught, just never ported to this shared test helper). Bench unchanged (router 651/100%, redteam recall 96.09%/FPR 2.99%). Needs a real phone on the same Wi-Fi for: actually scanning the QR code, confirming the mobile chat page renders and works, and the real-hardware look of the new Settings page.

Flagged, not fixed: a genuine LICENSE-file inconsistency (0 bytes vs. the README's MIT claim) found while reasoning through Piper's GPL-3.0 licensing. 677 tests, up from 647.

## Tier 6 — Planning depth

Scoped parallel execution for contiguous, independent, read-only (T0) plan steps only - real side-effecting steps still run strictly in order, on purpose, since most of Wave's tools touch shared state on the one machine the user is sitting at. Two real, previously-unguarded gaps closed in the shared backend: `open_website()` could be handed a URL with no real host, and `close_app("explorer")` would exact-match and kill the Windows shell itself. A lighter in-process test double for planner/executor tests that don't need a live LLM. 647 tests, up from original baseline.

## Tier 5 — Settings-page shortcuts, recent-actions polish, standalone timers

A deliberately scoped slice of the larger 50→150+ tool-count expansion: 15 new one-line "open X settings" tools backed by real per-OS settings-map growth, relative-time phrasing and consecutive-action grouping for the existing recent-actions tool, and standalone timers/a stopwatch (timers implemented as reminders for free persistence across a restart). 73 tools total, up from 50.

## Tier 4 — Handler decomposition, telemetry, eval harness

The ~50 tool-implementation methods living inside the main brain class moved out into `brain/handlers/`, grouped by domain - a genuine no-behavior-change refactor, verified by diffing every tool's registered spec byte-for-byte before and after. New per-turn telemetry/tracing. A new eval/regression harness (`bench/`) modeled on SARA's own, which immediately surfaced two real, honest gaps in the fast-path router (zero Devanagari coverage, a missed Hindi negation pattern) rather than reporting an inflated accuracy number.

## Tier 3 — Hardened web layer, reminder recurrence, workflows UI, composed skills

A shared retry-and-cache policy for all outbound web requests plus a URL allow-list; daily-recurring reminders; a dedicated Workflows page (saved multi-step command sequences); and a new `skills/` package for built-in skills that compose several raw tools into one (daily briefing, self-diagnostics).

## Tier 2 — Memory consolidation

A background pass that periodically reads recent chat history and saves durably-worth-remembering facts on its own, through the exact same storage path an explicit "remember this" already used - respecting the existing "don't save my chats" privacy setting.

## Tier 1 — Risk tiers, taint tracking, three-outcome guard

Every built-in tool classified T0 (read-only) through T3 (destructive), replacing a plain binary confirm flag. Per-turn taint tracking for whether a turn has read anything untrusted. A three-outcome guard (run/confirm/deny) instead of confirm-or-not, reaching the planner's step dispatch too.
