# Changelog

This file tracks Wave's tier-by-tier build, not semantic-version releases - each entry is one roadmap tier, not a numbered version. Full detail for Tiers 10-22 lives in the matching "Shipped in Tier N" section of [`Readme.MD`](Readme.MD) and the matching "Status — shipped" block in [`docs/ROADMAP_BEAT_SARA.md`](docs/ROADMAP_BEAT_SARA.md); this file is a summary, not the source of truth.

## Tier 47 — Fresh answers to time-sensitive questions, and the PC at a glance (2026-11-25)

SARA decides in code when a question needs the web, and tells its model what's on the PC; Wave only told the model (Tier 42) to call get_live_information for "latest/current/today's" questions - and checking that tool for this tier showed its search was broken: the `duckduckgo_search` package (since renamed `ddgs`) answered "petrol price in Delhi today" with a Chinese page about Netflix and "who is the current RBI governor?" with "electric current is expressed in amperes". Now:
- **The search works** (`web/web_ops.py` ask_internet, behind get_live_information too): `ddgs` when installed (now in requirements.txt), up to three results with their titles, and any result that doesn't name at least half of the question's own words is dropped - no answer beats a wrong one handed to the model as fresh. Live: "who is the current RBI governor?" -> Wikipedia's "Sanjay Malhotra is the twenty-sixth governor ..." in 2.4 s.
- **Time-sensitive questions are searched first** (`brain/grounding.py`): a question - not a command - with a recency cue ("latest", "current", "right now", "aaj ka rate", "abhi ka", "who won", "price of", "kitne ka hai", who holds a post: "current RBI governor", "india ka captain kaun hai") that isn't about the user and isn't one of Wave's own tools' (weather, news, time, battery ...) gets one web search, 6 s at most, before the model is asked; Hinglish is searched the way engines understand it ("petrol ka rate kya hai aaj Delhi mein?" -> "petrol rate today Delhi"). The results go to the model as a system message of their own, marked as web content - the turn counts as having read the web, so Tier 1's taint rules apply - never mixed into the user's words. Nothing found in time: the model answers as before.
- **One line about the PC** (`brain/context_line.py`) in every prompt: "ON THE PC RIGHT NOW: Brave is in front; battery 85% (charging)" (live, on the owner's laptop) - the app's name (never Wave itself), the battery, read at most every 5 s. A window's title can hold a document name, a chat or an email subject and the prompt goes to the cloud model, so titles are left out unless `CONTEXT_WINDOW_TITLES=true`, and even then never for banking, password, login or private-browsing windows.

`WEB_GROUNDING` and `CONTEXT_LINE` (true) turn them off, as `tests/_phase4_support.py` does for the test suite. 15 new tests in `tests/test_tier47_grounding_context.py`.

## Tier 46 — Memory: people, the past, fading, and a memory bench (2026-11-25)

SARA's Memory 2.0 follows people ("where does my sister work?"), answers about the past ("what did I tell you last Monday?"), lets unused memories fade, and measures all of it with a memory bench. Wave had none of the four. A new memory bench (`bench/memory_bench.py`, modelled on SARA's) runs scenarios - facts, messages and "forget that" over weeks, then questions - on Wave's own pipeline, with 22 background facts so only the most relevant facts reach the prompt, judging exactly the lines the model would get. Its first run showed a bigger problem: the right fact is often the most similar but below the 0.35 floor ("where do I live now?" is 0.20 similar to "city: Jaipur"), and with nothing above it the prompt got the first eight facts in alphabetical order. Now:
- **Ranking by similarity and shared words** (`brain/memory_rank.py`, as SARA mixes in word overlap): a question's words, and the words a fact's label uses for the same thing ("live"/"rehta" -> city, address; "kaam" -> job, workplace; "mithai" -> sweet; "called"/"naam" -> name), count fully in the label and half in the value; always the best eight, never the alphabetical ones.
- **A people graph** (`brain/people_graph.py`): the user's own clear statements - "my sister's name is Priya and she works at Infosys", "mere dost Rohan Pune mein rehte hain", "meri didi Neha Delhi mein rehti hai" - are remembered as `priya_relation: sister`, `priya_works_at: Infosys` (no model call; a name must be Capitalised or come after "name is"/"naam", so "my sister is sick" makes no one), and a question naming a relation (English or Hindi: behen, didi, bhai, dost, maa ...) or a name brings that person's facts first - including the ones the model saved its own way ("sister_name: Priya", "priya_birthday"). A relation nobody has brings nothing.
- **The past from the user's own words** (`brain/episodic_recall.py`): "what did I tell you last Monday?", "kal maine kya kharida tha?" (kal with a past verb = yesterday), "parso", "two weeks ago", "last week", "what did I tell you about the cricket match?", "exam ke baare mein maine kya bataya tha?" put the user's own messages from that day/week, or about that thing, in the prompt with their dates - only while chats are saved to disk, never one holding something the user asked Wave to forget.
- **Fading** (`db.archive_weak_memories()`, at start): a fact Wave picked up from conversation that is never recalled fades like SARA's strength, importance x exp(-days / (60 x (1 + 0.5 ln(1 + uses)))); below 0.05 (about 4.5 months unused) it is set aside - only once there are more than 40 facts, never one the user asked Wave to remember or one about a person, and never deleted: the memory screens still list it, a clearly matching question brings it back, recalling or saving it revives it.
- The memory part of the prompt moved to `brain/memory_context.py`, so the bench reads exactly what the model gets.

Memory bench (`bench/results/MEMORY.md`): 36 scenarios / 54 questions went from 64.8% to 100% (multi-hop 75 -> 100%, temporal 27 -> 100%, history 25 -> 100%, contradiction 62.5 -> 100%); the held-out set, 18 questions written after the ranking was settled and run once, from 55.6% to 100% - no forgetting leak and no false memory in either; retrieval ~42 ms. `MEMORY_PEOPLE_GRAPH`, `MEMORY_EPISODIC`, `MEMORY_DECAY` (all true) switch the parts off, as `tests/_phase4_support.py` does for the test suite. Tier 35's one-hop test now mocks the new ranking. 20 new tests in `tests/test_tier46_memory.py` (the bench itself on the real model when it's downloaded).

## Tier 45 — Everyday commands in other words, without a model call (2026-11-25)

The fast path (`brain/intent_router.py`) knows exact phrasings; "the screen is too dark", "bring the volume down", "move on to the next song", "kitne baj gaye" missed it and cost a model round trip (and a slice of Groq's per-minute quota) for a volume nudge. SARA adds a semantic fallback: compare the sentence with example phrases of each intent and run the closest. New `brain/semantic_intents.py` does that with the sentence model Wave already uses for memory (all-MiniLM-L6-v2) - for 20 low-risk tools, always run with no argument (volume, mute, brightness, media keys, screenshot, time, date, battery, weather, news, reminders, to-dos, briefing, clipboard, minimise all; nothing that locks, closes, deletes or sends), tried after the fast path, the planner and the exact answers, and run through the same gate and audit as the fast path (source `semantic_intent`).

An embedding alone isn't safe to act on - measured on that model, "reduce the volume" sits closer to "make it louder" than to "make it quieter", "brightness down" to brightness UP, "record my screen" to taking a screenshot, "set a reminder" to listing them. So the embedding only picks the family (volume, brightness, media, ...), at least 0.60 similar and 0.05 ahead of the next, and the words decide: every word must be one that family uses ("weather in Pune", "cricket ki khabar", "time complexity", "max volume", "not loud enough" all fall out), its key word must be there, and inside a family the direction comes from cue words, complaints first ("too loud" -> down, "too dark" -> brighter); no cue, or two that conflict, and nothing runs. Negated, hypothetical, conditional, compound and how/why sentences, numbers, yes/no questions about the switches ("is the volume muted?") and Devanagari are never tried. A turn never waits for the model to load (it loads in the background at start).

Measured on 112 held-out paraphrases plus ~190 traps (antonyms, negations, narratives like "I took a screenshot yesterday", remarks like "it's late", other tools like "close all windows") and the bench's 560 sentences: the fast path alone caught 29 of the paraphrases, with this 93, and nothing ran wrongly; `match()` takes ~25 ms. Without the sentence model it stays off. `SEMANTIC_INTENTS=false` turns it off, as `tests/_phase4_support.py` does for the test suite. 27 new tests in `tests/test_tier45_semantic_intents.py` (the measured cases run on the real model when it's downloaded).

## Tier 44 — Wi-Fi, Bluetooth and light/dark mode, switched for real (2026-11-25)

SARA turns Wi-Fi and Bluetooth on and off and switches the theme itself; Wave only opened the Settings page - and its `toggle_hardware` on Windows pressed Space on that page blindly, so "wifi on karo" turned an already-on Wi-Fi OFF ("Toggled Wi-Fi - check that it's now set the way you wanted"). Now:
- New tools `turn_wifi_on/off`, `turn_bluetooth_on/off` (Windows' own radio API through winsdk - the Quick Settings switch, no admin rights, ~0.1 s; NetworkManager/rfkill on Linux, networksetup/blueutil on macOS) and `switch_to_dark_mode` / `switch_to_light_mode` (the "Choose your mode" registry values for apps and Windows together, then a broadcast so open windows repaint; GNOME's color-scheme on Linux, System Events on macOS). An already-on radio stays on, and each change is undoable ("wapas kar do").
- Turning a radio OFF asks first (`brain/tiers.py` T2, with its own confirmation sentence): without Wi-Fi Wave's AI answers stop, and Bluetooth off drops a Bluetooth headset's mic.
- The fast path routes one radio with a clear on/off ("wifi band karo", "enable bluetooth", "ब्लूटूथ बंद करो") to these tools, and "dark mode", "dark mode lagao", "dark mode band karo" (= light mode), "switch to light mode" to the theme ones - a sentence that only mentions dark mode ("what is dark mode?") isn't a command. Both radios at once go to the model (each one's own confirm-gated tool); the hotspot stays `toggle_hardware`, which no longer blind-toggles a radio.
- `SYSTEM_TOGGLES=false` turns the real switching off - as `tests/_phase4_support.py` does, so no test can flip a real radio or theme.

On the owner's laptop the radio API reads Wi-Fi (on) and Bluetooth (off) in 0.08 s; nothing was switched in testing. Tests that pinned the old routes (Tier 8/11/17) and the 135-rule count (now 136) were updated on purpose; 12 new tests in `tests/test_tier44_radios_theme.py`, 13 new bench rows.

## Tier 43 — Open any installed app at once (2026-11-25)

The second SARA comparison found Wave still opened any app it had no shortcut for by driving the Start menu - press Win, type the name, press Enter: over a second of fixed waits, and when the Start menu didn't take focus the name was typed into whatever window was in front. SARA keeps an index of installed apps and launches from it in milliseconds. New `automation/app_index.py` does that on Windows from Windows' own list of Start-menu apps (`Get-StartApps` - desktop programs and Store apps alike, each with its AppID), built in the background at start-up (it takes ~10 s on the owner's laptop, so the last list is kept in `<DATA_DIR>/app_index.json`, git-ignored, and used at once) and refreshed every 30 minutes. A name resolves to an app by exact name, then a nickname ("vs code", "calc", "cmd"), then all its words among the app name's words, then a close spelling ("notepd" -> Notepad); anything vaguer, or an app that isn't installed, goes the old Start-menu way as before. Launching is `explorer.exe shell:AppsFolder\<AppID>` with an AppID from Windows' list only - the user's words never become a path or a command - and uninstallers never enter the index. On the owner's laptop: 106 apps; "chrome", "calc", "vs code", "whatsapp", "word", "cmd", "task manager" all resolve in under 4 ms. `APP_INDEX=false` turns it off, as `tests/_phase4_support.py` does for the test suite. 8 new tests in `tests/test_tier43_app_index.py`.

## Tier 42 — The smaller gaps: exact answers, looking things up, instant announcements (2026-11-25)

The last of the gaps to SARA's 12 Nov code, in one tier:
- **Exact answers, worked out in code.** "25 december mein kitne din bache hain?", "45 din baad kaunsi date hogi?", "what day was 15 august 1947?", "2400 ka 15 percent?" were the model's to work out token by token (and to get wrong, and each cost a call). New `brain/exact_answers.py` answers them in code before the model is asked - days until or since a date (fixed days like Christmas or Republic Day by name; lunar-calendar festivals like Diwali still go to the model), a date N days or weeks from today or ago, the weekday of a date, and percentages - in the language they were asked in ("25 December mein 30 din baaki hain."). Anything else goes on to the model as before.
- **Looking time-sensitive things up.** The `get_live_information` tool was always offered, but nothing told the model to use it; it now must for anything latest/current/today's/prices/scores/news/who-holds-a-post-now, "instead of answering from memory: what you learned in training is months old" (SARA grounds such questions with a web search).
- **Instant announcements in the cloned voice.** Since Tier 33 the wake and sleep announcements ("Systems active.", "Standing by.") are spoken in the cloned voice, i.e. synthesised by XTTS-v2 each time (seconds on the CPU) - and in Neerja's voice while it was still loading. They're now rendered once, right after the voice process loads (yielding to any real speech), kept on disk per voice sample in `<DATA_DIR>/voice_cache/clone/` (git-ignored), and played straight from there - right after a restart too, before XTTS-v2 is up. A new voice sample means new renderings. `TTS_CLONE_PREWARM=false` turns it off, as `tests/_phase4_support.py` does for the test suite.

8 new tests in `tests/test_tier42_small_gaps.py`.

## Tier 41 — Answers in the user's own style (2026-11-25)

SARA learns the length its user likes - asking for detail ("samjhao") or brevity ("chhota batao"), interrupting - and answers Roman-script Hindi in Hinglish. Wave's system prompt said neither, and live (Tier 34's check) Groq's model answered "hello wave, kaise ho?" in Devanagari. New `brain/style_profile.py` adds a STYLE section: the language of THIS message decides the reply's - Roman-script Hinglish gets Hinglish in Roman letters ("never in Devanagari"), Devanagari gets Hindi, English gets English, and a message too short to tell goes by the user's usual script - and once a clear lean shows, the length the user prefers ("likes detailed, thorough answers" / "prefers short, to-the-point answers"), from counts of detail and brevity requests and barge-ins (both mic workers report them), recent ones weighing more. Live after the change: "hello wave, kaise ho?" -> "Hi! Main theek hoon, aap kaise ho?" (1.0 s). Counts in `<DATA_DIR>/style_profile.json` (git-ignored); `LLM_STYLE_PROFILE=false` stops the learning and the length line (the language line always applies), as `tests/_phase4_support.py` does for the test suite. 8 new tests in `tests/test_tier41_style_profile.py`.

## Tier 40 — Instant answers to questions already answered (2026-11-25)

"What is photosynthesis?" asked again cost another model call and another slice of Groq's per-minute quota for the same answer. SARA caches final answers to stable, non-personal knowledge questions; new `brain/response_cache.py` does that for Wave, conservatively, since a wrong cached answer is worse than a slow one. Only a self-contained general-knowledge question is ever cached: nothing about the user (my, mujhe, mera, you ...), time or news (today, latest, abhi, price, weather, score ...), the PC (open, this file, screen, volume ...), the conversation (it, that, uska, ye ...), or small talk and things that should differ each time (kya haal hai, jokes, stories, suggestions). Only a plain model answer is stored - no tool called, nothing failed - keyed by the normalised question, the model that answered and a persona version; entries expire after `LLM_CACHE_TTL_DAYS` (14) and at most 300 are kept, in the main database. Live on Groq: "What is photosynthesis?" took 1.06 s the first time (gpt-oss-20b) and 0.02 s the second, with no model call. `LLM_RESPONSE_CACHE=false` turns it off, as `tests/_phase4_support.py` does for the test suite so a fake model's answer can never land in a real database. 9 new tests in `tests/test_tier40_response_cache.py`.

## Tier 39 — Other apps turned down while Wave listens or talks (2026-11-25)

With YouTube or Spotify playing, the mic hears the music with the user and the user hears Wave over the music. SARA ducks: it lowers other applications' volume while it listens, then puts it back. New `voice/ducking.py` does that for Wave while it's AWAKE (both UIs' mic workers report their mode) or speaking: every other app's audio session (Windows Core Audio per-app volume, through pycaw - nothing system-wide) plays at `AUDIO_DUCK_LEVEL` (0.3) of its own volume, an app that starts playing mid-conversation included, and gets it back 1.2 s after Wave is idle again (no pumping between sentences). Wave's own process and its children are never touched; muted sessions are left alone; the original volumes are written to disk before anything changes and put back at the next start if Wave was closed or crashed while ducking; a session whose volume the user changed in the meantime is left as they set it; without pycaw/COM nothing happens at all. On the owner's laptop pycaw sees two sessions (Realtek's console and Chrome) and reads and sets them. `AUDIO_DUCKING=false` turns it off - as `tests/_phase4_support.py` does for the test suite, so a test's mic worker going AWAKE never turns a developer's real apps down. 9 new tests in `tests/test_tier39_ducking.py` (a fake mixer).

## Tier 38 — "The conversation so far" for long chats (2026-11-25)

Each request carries only the newest 16 messages (within `LLM_HISTORY_CHARS`, since every token counts against Groq's per-minute quota); older ones simply vanished, so twenty minutes into a conversation Wave no longer knew how it had started. SARA folds the turns that leave its window into a short running summary with one small background model call. New `brain/rolling_summary.py` does that for Wave: once 6 messages have dropped out of the window, one background call to the fast model (Tier 34) folds them into the summary so far (`LLM_SUMMARY_MAX_CHARS`, 600), and the system prompt gets it as "EARLIER IN THIS CONVERSATION". It belongs to the current conversation only - messages older than 12 hours aren't folded and an old summary isn't shown - and clearing the chat history clears it. Messages containing something the user asked Wave to forget (Tier 35) aren't folded, and a summary that mentions one isn't used. At most one call per 30 s, in the background, never delaying a reply; saved in `<DATA_DIR>/conversation_summary.json` (git-ignored). Live on Groq (gpt-oss-20b, 1.3 s), six Hinglish messages about a trip became "The user is planning a 5-day trip to Goa starting 12 December with their wife. They want a beach-side hotel and a budget of about ₹40,000. Wave will look for options." `LLM_ROLLING_SUMMARY=false` turns it off, as `tests/_phase4_support.py` does for the test suite. 8 new tests in `tests/test_tier38_rolling_summary.py`.

## Tier 37 — The names Whisper should know (2026-11-25)

Whisper turns names it hasn't seen into near-misses ("Jaipur" -> "Jypur"). SARA puts the user's names in Whisper's prompt - by its own measurement English word errors went from 5.7% to 2.1% on clean audio (9.3% -> 7.7% at 8 dB of noise), ~10 ms a decode, and no listed name ever appeared on silence or noise. Wave's prompt had only the wake words and a style line. New `voice/vocabulary.py` adds, after them: `STT_EXTRA_VOCABULARY` (.env, comma-separated), the names in Wave's memory (a short fact under a name-ish key - name, wife, sister, friend, city, pet ... - gives its value; any Capitalised word in a short fact counts too; the Tier 35 date notes don't), and a few apps Whisper garbles (WhatsApp, YouTube, Spotify, Instagram) - at most 24 words, cached for 60 s. On the owner's laptop that is 2 names from memory plus the 4 apps. `STT_VOCABULARY=off` turns it off; `tests/_phase4_support.py` turns it off for the test suite (like the speaker check), so tests never read a developer's remembered names. 6 new tests in `tests/test_tier37_vocabulary.py`.

## Tier 36 — Don't cut the speaker off mid-sentence (2026-11-25)

Wave ended an utterance after 450 ms of silence, whatever had been said, so a pause inside a sentence - "mujhe kal subah ... yaad dilana ki doctor ke paas jana hai" - became two commands: the first half was answered on its own, the rest lost or misread. SARA's adaptive endpointing looks at the words. Wave now does that one step later, on the transcript (`voice/stt.py`'s `_continue_unfinished()`, new `voice/endpoint_cues.py`): a transcript that sounds cut off - ending on "and/or/but/to/the/because/um", "aur/ki/ke/ka/ko/se/mein/lekin/matlab/uske baad", "और/की/के/तो", or trailing off with "..." or a comma - waits up to `STT_CONTINUATION_WAIT_S` (1.6 s) for the rest, longer while the speaker is still talking (`CaptureEngine.speaking`, at most 12 s), and the two are joined into one command (up to 3 joins). A question ending in "?" counts as finished, and so do phrasal endings like "turn the wifi on", "log in", "help me", "close this tab". Not while Wave is talking; the rest goes through the speaker check like anything else, and isn't wake-gated (it's the rest of a command that was). `STT_CONTINUATION=false` turns it off. 10 new tests in `tests/test_tier36_endpointing.py`.

## Tier 35 — Memory 2.0: a past, real dates, one-hop recall, and forgetting that sticks (2026-11-25)

SARA's Memory 2.0 keeps what a fact used to be, understands time, joins related facts and makes "forget" stick (its own bench: 0% false memories, 0% forgetting leaks). Wave's memory was a flat key -> value table where a new value simply overwrote the old one. Now (`database/db_manager.py`, new `brain/memory_time.py`):
- **A changed fact keeps its past.** New `memory_history` table: saving "city: Delhi" over "city: Jaipur" records the change, and the prompt shows `city: Delhi (before: Jaipur, changed 2026-11-25)`, so "pehle kahan rehta tha?" has an answer. `get_memory_history()`.
- **Relative dates get their real date.** A fact saved as "doctor appointment kal" was wrong a day later. `memory_time.annotate()` writes the date it meant next to it - "kal (Thu 26 Nov 2026)" - for kal/parso (tomorrow or yesterday by the verb: "kal gaya tha" is yesterday), aaj, next/last monday, next/last week, "3 din baad", "2 days ago", weekdays, in English, Hinglish and Hindi; "aaj kal" ("these days") and a bare "sun"/"sat" are left alone, and so are calendar dates ("12 march" - a birthday recurs).
- **One-hop recall.** When there are more facts than go in the prompt, the ones the question matches bring along the facts their short values point at: "sister_name: Priya" brings "priya_birthday", so "meri behen ka birthday kab hai" gets both halves.
- **Forgetting sticks.** `forget_memory` now also deletes the fact's history and remembers it as forgotten (`memory_forgotten`): the background memory consolidation won't learn it again from old conversation, and messages containing it are left out of the chat history sent to the model. Saying it again on purpose ("remember ...") clears that.
- **No guessing.** The system prompt tells the model to say it doesn't know a personal detail it wasn't given (and offer to remember it), instead of making one up.

Checked against a copy of the owner's real database: the new tables are created next to the 3 existing facts, which stay as they were. 12 new tests in `tests/test_tier35_memory.py`.

## Tier 34 — The right model for each request (2026-11-24)

Compared with the current SARA (its 12 Nov code), Wave's biggest gap was SARA's model router: it picks a cheap/fast or a main model per request and learns from how the answers land, while Wave sent every turn to `openai/gpt-oss-120b` and moved to a backup only after a 429 - although on Groq's free tier each model has its own 8,000-tokens-a-minute quota, and Wave's slow or failed replies were mostly those 429s. New `brain/model_router.py`: everyday turns go to a fast model (`LLM_FAST_MODEL`, on Groq `openai/gpt-oss-20b` by default), and long, multi-step, code, writing ("leave application likho"), "explain in detail / samjhao", comparison, maths and planning requests - and anything with an attachment - go to `LLM_MODEL`. Each keeps the other as its fallback (`_models_for_request()`, models sitting out a rate limit go last), and a fast model that fails outright hands the turn to the main one. It learns: when the turn after an answer is a correction ("galat hai", "that's wrong", "phir se batao") or the same question again within 3 minutes, that kind of request (language x length x question-or-not) counts a miss; one whose fast answers miss 3+ times and at least a third of the time goes to the main model from then on, and gets another try on the fast one after 3 days (counts in `<DATA_DIR>/model_router.json`, git-ignored). `LLM_ROUTER=shadow` decides and logs without using it; `off` turns it off. Background jobs - memory consolidation, reminder rewording, proactive lines - now ask the fast model too, so they stop spending the main model's quota. Live on Groq: "hello wave, kaise ho?" went to gpt-oss-20b and was answered in 0.8 s; "explain in detail how a refrigerator keeps food cold" went to gpt-oss-120b (4.0 s). The first live try of that one also showed an old problem: gpt-oss-120b sometimes spends its whole token budget reasoning and returns no text - `think()` returned "" and the streamed reply said "taking longer than expected". Both now ask once more with little reasoning and more room (`_retry_empty_answer()`). 20 new tests in `tests/test_tier34_model_router.py`.

## Tier 33 — The cloned voice "r1" in the voice picker, a start that can't hang, and "r2" as the owner's voice (2026-11-23)

The owner reported that Wave wasn't speaking in the WhatsApp voice, and named the two recordings: r1 (the WhatsApp voice note, someone else's voice) is the voice Wave speaks with; r2 (a phone recording of the owner) is the voice Wave should recognise. They asked for r1 to sit in Settings -> Voice, as Wave's primary default voice.

- **Why Wave spoke in Neerja.** Started from VS Code, Wave launched its voice process, which never got ready: idle about two seconds of CPU in (0.21 GB - right after its imports, measured), where coqui-tts's `TTS(model_name)` checks the licence (asking with `input()` when `tos_agreed.txt` isn't found) and asks huggingface.co about the model on every start. Wave would have waited 15 minutes, speaking Neerja meanwhile, and nothing said why. The voice process now loads XTTS-v2 straight from the downloaded copy, without the network (`voice/clone_xtts.py`'s `cached_model_dir()`: Hugging Face's cache with `local_files_only`, after checking the licence the way coqui-tts does); its stdin is NUL for everything but the requests, so a question from any library fails at once instead of waiting forever (`voice/clone_worker.py`); its output goes straight into `wave_voice_clone.log` in the data folder instead of a pipe (`voice/clone_client.py`, git-ignored, rolled at 1 MB); and while it loads Wave's log says so every 60 s with the process's last line, as does a failed start. Measured with the network made unreachable: ready in 16 s; the same sentence with a fixed seed came out the same as with the old loading (6.50 s, samples within 1.5e-5). In the real web back end: "Voice clone ready from 'avatar_rig\r1.wav' on cpu in 16.0s", then a sentence spoken in the cloned voice (4.3 s of audio in 7.4 s).
- **r1 is the voice sample, and in the picker.** The sample Wave already had is r1: its 21 s are r1 from 35.3 s on (audio correlation 1.000), so it was renamed `avatar_rig/r1.wav` (the user's `wave_settings.json` points there). Both UIs' Settings -> Voice now list the cloned voice first, named after its sample ("r1 — Cloned voice"), picked by default whenever a sample is set; picking an edge-tts voice turns it off (`VoiceEngine.set_voice()`, `use_clone`, `voice_choice`), picking it again turns it back on and loads it. "Build avatar" with a sample makes it the voice. ## Tier 31 — Wave speaks in your own voice, for real (2026-11-19)

The user asked what had happened to the voice sample they gave (a 65-second WhatsApp note, trimmed on 2026-11-11 to its longest clean 21 seconds, `avatar_rig/voice_reference.wav`), then asked for Wave to actually speak with it. It never had, in either UI: `wave_settings.json` still pointed at the Linux build sandbox's path (`/home/claude/wave/...`), so the desktop UI quietly fell back to edge-tts, and the web UI never restored the sample at all. With the user's agreement to Coqui's non-commercial CPML licence the XTTS-v2 model was downloaded (1.87 GB, SHA-256 checked against Hugging Face; coqui-tts's own prompt wrote its `tos_agreed.txt`, so the windowed app never stops at that console prompt). Running it for real then turned up five more problems, each measured on the user's laptop (i5-13450HX, RTX 3050 6GB):

- `torchaudio.load()` needs FFmpeg's DLLs since torchaudio 2.9 (torchcodec), so XTTS's own loader failed on every sentence. The sample is read with soundfile and the voice latents are worked out once per sample file, with the model's own config values (`voice/clone_xtts.py`).
- Windows 11's power throttling (EcoQoS) moved Wave's process to slow efficiency cores about a second into any sustained work: torch's maths went from 0.12 ms to 1.8 ms per matrix multiply. Both launchers and the voice process opt out (`monitoring/power.py`, `POWER_THROTTLING_OPT_OUT`), which also keeps Whisper at full speed while Wave's window isn't in front.
- Inside Wave's process, Python's GIL made XTTS-v2 unusable: its token loop gives up and re-takes the GIL about a thousand times per token, so one busy pure-Python thread turned a 2-second sentence from ~4 s into more than 4 minutes, and in the real app one sentence took 568 s while the mic stream kept dropping ("Mic stream reopened") because XTTS starved the audio threads in turn. XTTS-v2 now runs in a process of its own (`voice/clone_worker.py`, started and fed by `voice/clone_client.py`'s `CloneVoiceProcess` over a small stdin/stdout protocol; it exits when Wave does). With a busy thread in Wave's process the clone still ran at its normal speed, and torch is no longer loaded into Wave's process at all.
- Every sentence waited for its own synthesis (~1.8x its length on the CPU). `prefetch()` now queues cloned sentences on one ordered worker, so the next one is made while the current one plays; both UIs start the voice process in the background at start-up (`warm_up_clone()`, ~15-20 s), and until it is up sentences go out in the edge-tts voice instead of waiting in silence.
- The 20 s playback watchdog could cut a cloned sentence off mid-synthesis; it now allows for the synthesis (`_watchdog_seconds()`).

`TTS_CLONE_DEVICE=auto` runs XTTS-v2 on the GPU as soon as PyTorch has CUDA; wave_env ships the CPU build (the CUDA one is a separate ~1.9 GB install, `docs/VOICE_LOCAL.md`). Measured: speaker similarity to the sample 0.63-0.76 for cloned lines vs 0.21 for edge-tts's Neerja; synthesis ~1.8x real time on the CPU (int8 weights reached ~1.2x but weren't adopted - a quality risk for a small gain) and ~0.4x on the GPU. In the real web app on the CPU, with Whisper transcribing room audio alongside, a typed question's first cloned audio came 13 s after sending (21 s before the move to a separate process) and sentences ran at 2.4-4.2x real time. 43 new tests (`tests/test_tier31_voice_clone_live.py`, including the process plumbing against a stand-in worker); `tests/test_tier25_voice_clone.py` follows the process interface; `tests/test_tier24_web_ui.py` no longer reads the user's real `wave_settings.json` (with the restore above, that started loading the real model in the middle of the tests).

## Tier 29 — Replies that arrive, and lips that move only with the voice (2026-11-18)

The user reported that replies were unreliable - sometimes "(no reply)", sometimes an error, usually very late after a long "thinking" - and that the Dodo character's lips kept moving while no voice came out. Their own log showed why. Every request in a session got "429 Too Many Requests": Groq's free tier allows 8,000 tokens a minute per model, a request was ~3,600 tokens, a reply that uses a tool needs two, and the mic - permanently AWAKE once woken - kept turning room noise into questions ("Gather real", "Gatya", "You have eaten."), each one another cloud request that also cut off the reply in progress. Fixes: the SDK client no longer retries by itself (`max_retries=0`); `WaveBrain._llm_create()` moves a rate-limited request at once to a backup model with its own quota (`LLM_FALLBACK_MODEL`, default openai/gpt-oss-20b on Groq), keeps a per-model cooldown from Retry-After, waits once if a model frees up within `LLM_RATE_LIMIT_WAIT_S` (10 s), retries a 5xx/dropped connection once, and otherwise answers "the AI service is busy - ask again in about N seconds" instead of an error; the Ollama fallback is skipped after a 0.4 s check when nothing listens (remembered 60 s); history sent with a request is capped (`LLM_HISTORY_CHARS`, 4,000 chars, no message over 1,200); tool lists dropped to `LLM_MAX_TOOLS`=20 and are no longer padded with tools the turn gave no sign of needing (small talk now carries 12, ~1,100 tokens instead of ~2,200). Web UI mic: while AWAKE, a transcript of three words or fewer, below `AWAKE_MIN_CONFIDENCE` (0.5), without the wake word and unknown to the intent router is ignored as noise, and AWAKE quietly returns to waiting for the wake word after `AWAKE_IDLE_SLEEP_S` (60 s) of nothing for Wave; recognized speech is now logged with its confidence. Chat: every reply carries a turn number back on chat_chunk/chat_done, so a cancelled turn finishing late can no longer end the next reply's bubble with "(no reply)" (which is also why answers were heard but not shown). Dodo: the avatar used to switch to SPEAKING the moment a reply was requested, and the page invented "chatter" when no audio curve had arrived - so her lips moved through every silent wait. Now the bridge marks SPEAKING only when TTS audio actually starts (voice/tts.py's on_playback_start, which also gives the web UI its time-to-first-audio figure), the mouth moves only from the loudness curve of audio really playing, and a stopped sentence stops the lips too. Measured against the real Groq account at a normal pace: five questions answered in 1.7-16 s, none failing (they took 60-80 s or failed before). 16 new tests (`tests/test_tier29_reply_reliability.py`).
